### 1. 基线、范围和使用方法

- 本轮源码基线：`8f48d6cc084be91bcbaad90be43dac7181636cb4`；复核日期：2026-09-22（Asia/Shanghai）。文档与当前实现逐项对应，待实施设计与已有能力分别标记。
- 交付范围：运行稳定性风险分析、服务级时序图、加固任务设计、测试用例、故障预案和演练方案。**没有修改业务代码、配置、SQL或对外协议，没有实施生产故障注入。**
- 当前结论以本方案及其源码链接为准；每项风险关闭必须具备对应实现与有效测试证据。
- 当前为 Spring Boot 3.4.6 / JDK 21 / Servlet 主部署，混用响应式编排、阻塞 JDBC 和出站 HTTP/WS。用户确认WCM静态源、ALB文根、saas gateway（SaaS统一网关）和ADS Docker；当前ChatService、relayService与一体agentService共享DB与Redis。agentService包括管理、技能查询、统一chat和MCP，第三方intentService独立。目标要求各Region的ALB和ADS运行/控制面独立（P）；实际独立性、参数、数据复制和容灾实测仍待提供（E），见[部署与容灾设计](deployment.md)。
- 未来拆分为adminService、toolService、agentService，加上ChatService/relayService共五服务，初期仍共享数据资源；文档管理迁入agentService，大文件直传对象存储，必须转发的EDM文件采用独立worker。拆分、直传和资源隔离均为P，不能当作当前保护。
- “全盘”指全部入口仍有场景归属，主风险清单按高影响稳定性故障筛选；纯业务正确性和安全专项不在本方案范围；不意味着证明不存在未知风险。S=源码事实，L=本轮本地验证，U=用户确认架构，P=待实施目标，E=环境待验证；U/P不是生产验收证据，“具备缺陷触发条件”不等于生产已经发生事故。

#### 当前实现的关键语义

1. 当前统一chat与Relay MCP都依赖agentService，因此Relay不是独立故障备用。DomainAgent、intentService、relayService分别列为[R19](risks.md#r19)、[R20](risks.md#r20)、[R21](risks.md#r21)，与agentService自身的[R16](risks.md#r16)分开定位。
2. 仓库默认Intent关闭；开启后的重试、故障转Relay行为需同时评估下游余量。统一chat与Relay都有各阶段期限，但应用超时、本地Stop返回不证明远端任务停止。默认值及计时范围只维护在[依赖调用策略](scenarios.md#wait-budgets)。
3. 技能留存策略、附件校验和展示查询的失败语义不同，不能统一降级放行。新保护和服务拆分均需实装验收，不能把图中目标当作已有能力。
4. [R22 WebSocket连接与订阅洪峰](risks.md#r22)列入第一轮P1条件性加固：当前单用户/单连接限制不能替代实例总量、握手/控制速率及恢复并发预算。大量连接场景上线前必须完成T22及D05验证。
5. 容灾保留单写屏障，执行结果未知禁止自动重跑；FULL恢复受实际持久化范围约束，no-store不新增业务正文持久化。以上是安全恢复约束，不扩展为本轮业务正确性专项。

### 2. 覆盖矩阵与故障分析方法

入口与场景覆盖见[场景目录](scenarios.md#flows)，部署覆盖见[DEP01–DEP06](deployment.md)，风险关联仅维护[统一追踪矩阵](risks.md#risk-register)。

专项检查分别落在[覆盖矩阵](scenarios.md#coverage-matrix)、[事务与锁顺序表](scenarios.md#transaction-locks)和[全链路等待预算表](scenarios.md#wait-budgets)。检查数据库显式/隐式锁、JVM锁、事务传播与跨线程边界，并追踪排队、鉴权、连接、首事件、SQL/锁和取消后的真实释放；保留已有Session排序和短事务保护。潜在等待环必须经确定性交错实验确认，不能由多个方法各自持锁推断已发生死锁。

每场景只维护一张服务级图，差异用`alt/opt/loop`及简短说明表达。图只出现前端、网关、服务和资源，直接标出关键期限、重试及失败影响；源码证据集中在风险条目，外部内部策略标E。12张场景图加7张部署图共19张，不另保留代码级运行图。

风险审查采用“入口→等待→占用→副作用→提交→通知→清理”顺序。对每个节点枚举：不可用、延迟、部分成功、数据过大、重复/乱序、取消、进程退出；对每个资源检查数量、字节、时间、作用域、释放和观测。CPU检查覆盖解析、递归脱敏、序列化、重试重连、数据库扫描与GC；仅有复杂调用链不能直接判定CPU缺陷，需要profile和增长曲线。

### 3. 服务目标、容量与观测契约

#### 3.1 SLI口径

以下是待实现/校准的观测契约，不表示现有Actuator已全部暴露。按部署版本、场景、provider、结果分类；日志关联runId/traceId，指标不使用用户ID、sessionId、完整URL等高基数或敏感标签。

| SLI | 分子/分母或计时边界 | 不能掩盖的失败 |
|---|---|---|
| 请求受理可用率 | 成功返回可核对Run标识的合法请求 / 合法受理请求；从入口至响应 | 网关5xx、过载拒绝、系统异常、未知结果；参数/权限拒绝另计 |
| 首业务事件延迟 | 已受理请求到首个对用户有意义的正文/交互/进度事件；另报run.started延迟 | run.started不是首个模型答案；超时和未产出必须计入失败分布 |
| Run完成率与时间 | 按provider/模式统计应完成Run的正确终态及持续时间 | WAITING_USER/ASYNC_WAITING分开统计，不把等待态算答案成功；用户取消单列 |
| 结果恢复成功率 | FULL恢复请求在约定期限内读齐已持久化范围且顺序/去重正确 / 有恢复需求请求 | 终态已入DB但前端未消费；no-store业务事件不纳入可回放承诺 |
| Stop本地收口 | 活动Run从接受Stop到合法终态及资源释放；自然完成已竞胜单列。WAIT取消另量Interaction/Binding及实际续跑Run收口 | 历史WAIT Run不要求改写CANCELLED；HTTP返回不等于远端已停，远端确认独立指标 |
| 故障放大与残留 | 每逻辑请求真实尝试/工具数、取消后在途任务数、恢复积压年龄及资源回落时间 | 不能只看外层已超时；任务仍执行、重试倍增或积压未降均未收口 |
| 服务RTO/任务RTO | 分别从故障开始到服务恢复、存量任务全部按策略收口 | 接口恢复但遗留RUNNING未处理不能宣布完全恢复 |
| RPO | 按已提交事实、实时事件、外部副作用分层核对 | FULL持久化承诺还依赖DB复制/备份；不在未知拓扑下承诺RPO=0 |

默认采用滚动30天作为讨论窗口，数值目标由业务负责人确认后冻结。测试运行单必须在开始前填写`受理/首事件/完成/恢复/Stop`预算；没有目标值只能报告测量结果，不能签署上线通过。

#### 3.3 容量验证方式

不能从租户200许可、下游64许可或Hikari10连接直接推算可承载用户数。先固定请求结构，再逐级加压得到安全承载点；同时测正常、故障降级、恢复及少一实例时的容量。

- WS容量分别测空闲连接、活跃推送、慢消费和集中重连；登记实例/租户连接、握手及控制消息速率、订阅校验与恢复并发、实例累计发送字节。4C4G或Tomcat连接参数不能直接换算安全WS连接数，按[T22](tests.md#t22)签认容量。
- 连接需求估算：`在途流数 × 每流事件速率 ÷ 每批事件数 × 每批持连接时间 + 其他业务占用`；模型用于选择压测区间，不作为性能承诺。
- 内存预算：JVM基础占用 + 活跃Run累计数据 + 各缓冲区/对象副本 + 连接发送数据 + 文件在途字节 + GC余量；还要给direct/native及进程额外占用留预算。
- 当前三服务、未来五服务及文档worker的所有实例数据库池、扩容及滚动发布重叠副本、治理保留和其他连接之和不得超过DB安全预算；隔离线程池或Redis命名空间不等于隔离共享资源。暂不全面读写分离，状态判断和Resume保持读取权威主库。
- 500MiB文档是目标容量，不是当前默认允许值。评估堆内副本、临时盘、慢上传连接及存储完整流生命周期；文件大小不是进程内存上限。按[W06](risks.md#w06)分别验收直传和隔离转发，不通过单纯调大multipart上限放量。
- 限额降低须验证忙响应及客户端退避；重试、重连、回源和Watchdog同时恢复时也必须受预算约束。
